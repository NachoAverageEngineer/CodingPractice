Loom & Anvil

A ground-up path into Minecraft Fabric mod development — no assumption you've built one before, even if you have. Every idea gets a short explanation, then something small to build with just that idea, then a bigger problem that forces you to combine it with everything before it. Written to run entirely from an iPad in Safari. Solutions stay hidden until you've actually tried; an on-demand hint is one tap away when you're truly stuck, and it will never just hand you the answer.

Start here

Orientation

You already know more Java than you're giving yourself credit for — loops, conditionals, methods, basic classes. What CodingBat doesn't teach is how a real, event-driven, multi-threaded Java application is put together, which is most of what Fabric modding actually is. This course closes that gap on purpose, in order: enough Java-the-language to stop guessing, then Fabric's own architecture, then the two things that trip up almost every self-taught modder — mixins and config files — done the way an experienced modder does them, not the way a copy-pasted tutorial does them.

One assumption this course makes on purpose Not that you've built a Minecraft mod before — even if you have. If AI wrote most of the code for something you've shipped, the part that matters most, reading an unfamiliar API and reasoning out what it does, probably didn't get built. Nothing here assumes you already know what a registry, a mixin, or a config loader is. If a term shows up before it's explained, that's a bug in this page, not a gap in you — say so and it gets fixed.
The iPad problem, solved honestly Compiling and running a Minecraft mod needs a JDK, Gradle, and a Java game client. No website can do that inside Safari with zero downloads — that's not a limitation of this site, it's just what a mod is. The fix is GitHub Codespaces: a full Linux dev machine that runs in your browser tab, free within GitHub's monthly hours. You'll write and build real code from your iPad; when something needs an actual graphical Minecraft client to eyeball, we lean on Fabric's own GameTest framework instead, which checks your mod's behavior automatically with no display at all. You'll rarely be blocked.

How each module is shaped

Every new idea follows the same rhythm: a short explanation, then a Try it — small enough to finish in a couple of minutes, using only that one idea. Every few ideas, a bigger Combine it forces you to use several of them together, including ones from earlier modules — that's the point where you find out whether you actually understood the Try-its or just skimmed them. Do the Try-its for real, in an actual file, even the ones that feel too small to bother with. Skipping straight to Combine It is the easiest way to convince yourself you understand something you don't.

How the hint button works

Every exercise has a real, correct solution hidden behind a ▸ Reveal solution toggle — written by hand, not by an AI, so it's something you can trust. Separately, most exercises have a Stuck? Ask for a hint box. It will never hand you the finished answer — it asks you a guiding question the first time, gives you a bigger nudge the second time, and walks through the approach in plain English (no working code for the actual exercise) the third. If you want the answer, use the solution toggle and be honest with yourself about whether you understood it or just copied it.

Module 1

The workshop: setting up in GitHub Codespaces

Everything below happens in Safari, from the repo page. No App Store, no Xcode, no local JDK.

Vocabulary check, before you touch anything

None of this comes up in CodingBat, so quickly: Gradle is a build tool — a program that reads a config file and turns your source code, plus other people's code your project needs, into a runnable thing. A dependency is someone else's code your project needs to compile against — here, that's Minecraft's own code and Fabric's libraries. Gradle downloads exactly the versions you specify and wires them in; you never manually hunt down a .jar file yourself. The JDK (Java Development Kit) is what actually compiles and runs Java — Codespaces installs one inside the container for you, which is the whole reason this works with nothing installed on the iPad itself.

1. Get your own copy of a working mod skeleton

Go to github.com/FabricMC/fabric-example-mod — this is Fabric's own official starter, kept up to date by the people who build the toolchain. Tap Use this template → Create a new repository and give it a name (call it loom-and-anvil if you want to follow along literally).

2. Open it as a Codespace

On your new repo's page, tap the green Code button, switch to the Codespaces tab, and tap Create codespace on main. GitHub builds you a container with Java and the tools preinstalled and opens a full VS Code in your browser tab — this is your IDE now, keyboard shortcuts and all.

Free tier, and a student bump Personal GitHub accounts get 60 hours a month on a 2-core Codespace (120 core-hours) plus 15GB storage, free — plenty for coursework. If you're using a school email, check whether it qualifies for the GitHub Student Developer Pack, which raises those limits.

3. Point it at Minecraft 1.21.11

Open gradle.properties in the file explorer. You'll set four values to match this course:

minecraft_version=1.21.11
yarn_mappings=<current 1.21.11 build>
loader_version=<current loader>
fabric_version=<current Fabric API for 1.21.11>

Fabric ships new build numbers often, so this page won't hardcode ones that go stale — open fabricmc.net/develop or the Fabric API versions page, filter to 1.21.11, and copy the current numbers in. Learning to find the right dependency version yourself is a real modding skill — tutorials that hardcode version numbers are usually the ones you find broken six months later.

4. Prove it builds headlessly

Open a terminal (hamburger menu → Terminal → New Terminal, or the shortcut your keyboard's Ctrl/Cmd key gives you) and run:

./gradlew build

First run downloads and deobfuscates Minecraft itself, so give it several minutes. A final BUILD SUCCESSFUL with no test failures is your entire toolchain working, end to end, with no display attached — remember that line, it's the signal you'll rely on for the rest of the course.

Combine it
Rename the mod: change the mod_id and mod name in gradle.properties and src/main/resources/fabric.mod.json to something of your own, then run ./gradlew build again and confirm it still succeeds.
Reveal checklist

You need to touch three places consistently: gradle.properties (mod_id, usually also the archives_base_name), fabric.mod.json (the "id" and "name" fields), and your Java package name if you rename that too (update the entrypoints paths in fabric.mod.json to match). Mismatch any of these and the build usually still succeeds but Minecraft refuses to load the mod later with a "duplicate/invalid mod id" style error — so this exercise is really practice at reading exactly what changed.

Module 2

Java, past CodingBat

CodingBat teaches you to reason about values — strings, arrays, conditionals. Fabric's codebase constantly leans on a handful of Java features CodingBat never exercises, because they're what large, long-lived codebases actually need. None of these are exotic — they're ordinary Java, just outside what a warm-up site tests. Take every Try-it seriously; they build directly on each other and feed the Combine It at the end.

Interfaces as contracts

An interface says "anything that implements me can do these things," without saying how. Fabric's own entrypoints are interfaces — ModInitializer just promises "I have an onInitialize() method," and Fabric Loader calls it without caring what your class is named.

public interface Greeter {
    String greet(String name);
}

public class FriendlyGreeter implements Greeter {
    @Override
    public String greet(String name) {
        return "Hey there, " + name + "!";
    }
}
Try it

Write an interface Soundable with one method, void makeSound() (no return value). Then write a class Cow that implements it, printing "Moo".

Reveal solution 
public interface Soundable {
    void makeSound();
}

public class Cow implements Soundable {
    @Override
    public void makeSound() {
        System.out.println("Moo");
    }
}

Lambdas: an interface implementation without the class

When an interface has exactly one method (a "functional interface"), Java lets you skip writing a whole class and just write that one method as a compact expression instead — a lambda. This matters more than it looks: Fabric API's events are all functional interfaces, and you'll write a lambda for almost every one of them in module 5.

Soundable cow = () -> System.out.println("Moo");
cow.makeSound(); // Moo

The () is the (empty) parameter list matching makeSound(); everything after -> is the method body. A method that takes parameters just lists them before the arrow: (player, world, hand) -> { ... }.

Try it

Rewrite your Cow class from above as a one-line lambda assigned to a variable of type Soundable, instead of a separate class.

Reveal solution 
Soundable cow = () -> System.out.println("Moo");

Records, for plain data

A lot of modern Fabric code — especially network packets — is small, immutable bundles of data. A record gives you a constructor, getters, equals, hashCode, and toString in one line, instead of the 20-line class you'd hand-write for the same thing.

public record Coordinates(int x, int y, int z) {}

Coordinates spot = new Coordinates(100, 64, -32);
spot.x();   // 100 — records auto-generate accessors named after the field
Try it

Write a record Coordinates(int x, int y, int z), create one for the point (100, 64, -32), and print just its y value.

Reveal solution 
public record Coordinates(int x, int y, int z) {}

Coordinates spot = new Coordinates(100, 64, -32);
System.out.println(spot.y()); // 64

Generics, briefly

List<Item> means "a list that only ever holds Items" — the compiler enforces it so you can't accidentally shove a String in and find out at runtime. You'll see this constantly in registries: Registry<Item>, Registry<Block>.

Try it

Declare List<String> tags = new ArrayList<>(); and add "sword" and "legendary" to it. Then, in one sentence, explain why tags.add(5); would refuse to compile.

Reveal explanation

List<String> is a generic type locked to String — the compiler knows at compile time that every element must be a String, so passing an int (auto-boxed to Integer) is a type mismatch it catches immediately, instead of letting the mistake surface later as a runtime ClassCastException somewhere far from where the bad value was added.

Static fields for identity and shared state

A static final field belongs to the class, not an instance — this is how a mod exposes its ID, its logger, and its registered objects so every other class can reach them without passing references around everywhere.

public class LoomAnvilMod {
    public static final String MOD_ID = "loom_anvil";
}
// anywhere else: LoomAnvilMod.MOD_ID
Try it

Add public static final int MAX_LEVEL = 10; to a class named Charm. From a completely different class, write the exact line of code that reads it.

Reveal solution 
int max = Charm.MAX_LEVEL;

Optional, instead of null-checking everything

Optional<T> forces you to explicitly handle "this might not have a value" instead of forgetting a null-check and crashing a server at 2am. Minecraft's own APIs use it a lot for lookups that might fail.

public Optional<String> findByName(String name) {
    if (name.equals("anvil")) return Optional.of("anvil");
    return Optional.empty();
}
Try it

Call your findByName with "iron" (which doesn't match) and, without an if statement, use .orElse("unknown") to get a fallback value out of it. Print the result.

Reveal solution 
String result = findByName("iron").orElse("unknown");
System.out.println(result); // unknown

Enums, for a fixed set of named options

An enum is a fixed, named set of constants. Minecraft uses them everywhere — directions, rarities, dye colors — because unlike a plain String, the compiler catches a typo ("comon" instead of "common") at compile time instead of silently misbehaving at runtime.

public enum Rarity { COMMON, RARE, LEGENDARY }

Rarity r = Rarity.LEGENDARY;
Try it

Write an enum AbilityTier with two constants, MINOR and MAJOR. Write one line of code that stores MINOR in a variable and prints it (an enum's toString() prints its constant name for free).

Reveal solution 
public enum AbilityTier { MINOR, MAJOR }

AbilityTier tier = AbilityTier.MINOR;
System.out.println(tier); // MINOR

try/catch, for things that can fail

Some operations — reading a file, parsing text as a number — can fail in ways the compiler can't prevent. try/catch lets you say "attempt this, and if it throws an exception, handle it here instead of crashing." You'll use this for real in module 7, loading a config file that might not exist yet.

try {
    int n = Integer.parseInt(userInput);
} catch (NumberFormatException e) {
    System.out.println("That wasn't a number.");
}
Try it

Write a try/catch around Integer.parseInt("banana") that prints "Couldn't parse that." instead of letting the exception crash the program.

Reveal solution 
try {
    int n = Integer.parseInt("banana");
} catch (NumberFormatException e) {
    System.out.println("Couldn't parse that.");
}
Combine it
Write an interface Ability with one method void activate(String playerName). Write a record AbilityResult(boolean success, String message). Write an enum AbilityTier { MINOR, MAJOR }. Write a class CheapenAbility implementing Ability with a public static final AbilityTier TIER = AbilityTier.MINOR; field, whose activate prints a message including both the player's name and the tier. Finally, put CheapenAbility and one more Ability of your own (a lambda is fine) into a List<Ability> and call activate on each in a loop.
Reveal solution 
public interface Ability {
    void activate(String playerName);
}

public record AbilityResult(boolean success, String message) {}

public enum AbilityTier { MINOR, MAJOR }

public class CheapenAbility implements Ability {
    public static final AbilityTier TIER = AbilityTier.MINOR;

    @Override
    public void activate(String playerName) {
        System.out.println(playerName + " activated Cheapen (" + TIER + ")!");
    }
}

// elsewhere:
List<Ability> abilities = new ArrayList<>();
abilities.add(new CheapenAbility());
abilities.add(name -> System.out.println(name + " activated a Spark!"));

for (Ability ability : abilities) {
    ability.activate("Finn");
}

Module 3

Anatomy of a Fabric mod

A Minecraft world runs as two logical halves even in singleplayer: an internal server simulating the world, and a client rendering it and reading your input. A dedicated server has no client half at all. Fabric makes you declare, per class, which side you're allowed to touch — get this wrong and your mod crashes dedicated servers with a ClassNotFoundException for a rendering class that simply doesn't exist there.

fabric.mod.json is the manifest, and "id" is a namespace

This file tells Fabric Loader what your mod is and which classes to call at startup — its entrypoints. The "id" field matters more than it looks: it becomes your mod's namespace, the prefix every item, block, and identifier you register will carry (loom_anvil:cheapen_charm), so it has to be unique among every mod that might ever load alongside yours, and it has to match everywhere it's used.

{
  "id": "loom_anvil",
  "entrypoints": {
    "main": ["com.example.loomanvil.LoomAnvilMod"],
    "client": ["com.example.loomanvil.LoomAnvilClient"]
  }
}
Try it — spot the bug

Here's a broken fabric.mod.json: "id": "loom_anvil", but the entrypoint reads "main": ["com.example.oldname.LoomAnvilMod"] — and the actual Java class lives in package com.example.loomanvil. What happens when Fabric Loader tries to start this mod?

Reveal answer

Fabric Loader looks for a class at exactly com.example.oldname.LoomAnvilMod — that class doesn't exist at that path, so loading fails immediately with a ClassNotFoundException, before any of your code ever runs. The mod id and the Java package are two independent strings; nothing keeps them in sync for you but you remembering to update both when you rename one.

Three initializer interfaces, three audiences

  • ModInitializer — onInitialize() runs on both client and dedicated server. Registries go here.
  • ClientModInitializer — onInitializeClient() runs only where there's a screen. Rendering, keybinds, HUD.
  • DedicatedServerModInitializer — runs only on a dedicated server. Rare, but exists for server-only setup.
public class LoomAnvilMod implements ModInitializer {
    public static final String MOD_ID = "loom_anvil";
    public static final Logger LOGGER = LoggerFactory.getLogger(MOD_ID);

    @Override
    public void onInitialize() {
        LOGGER.info("Loom & Anvil is warming up the forge...");
    }
}
Try it

Write a ModInitializer class named CheapenMod whose onInitialize() logs "Cheapen mod loaded." using a Logger the way LoomAnvilMod does above.

Reveal solution 
public class CheapenMod implements ModInitializer {
    public static final Logger LOGGER = LoggerFactory.getLogger("cheapen");

    @Override
    public void onInitialize() {
        LOGGER.info("Cheapen mod loaded.");
    }
}
Good practice Never reference a client-only class (anything under rendering, screens, or particle effects) from a class that also runs on the dedicated server — even a single unused import can crash a server the moment that class loads. When in doubt, keep client-only logic physically inside your client entrypoint's package.
Checkpoint

In your own words: why would a dedicated server never call onInitializeClient(), even if the class exists right there in your mod's jar file?

Reveal answer

onInitializeClient() is only invoked by the client-side bootstrap path — a dedicated server binary simply never instantiates a ClientModInitializer at all, so the class is never touched there. It's not sandboxing or permission-checking; Fabric Loader just never calls that entrypoint on that distribution. The class being present in the jar doesn't matter if nothing ever calls into it.

Combine it
Add a ClientModInitializer class that logs a different startup message, and wire it into fabric.mod.json's "client" entrypoint list alongside your CheapenMod in "main". Run ./gradlew build — it should still succeed, since build only exercises server-side game tests.
Reveal solution 
public class CheapenClient implements ClientModInitializer {
    @Override
    public void onInitializeClient() {
        CheapenMod.LOGGER.info("Cheapen client-side rendering ready.");
    }
}
"entrypoints": {
  "main": ["com.example.loomanvil.CheapenMod"],
  "client": ["com.example.loomanvil.CheapenClient"]
}

Module 4

Registries: how Minecraft knows your stuff exists

Every item, block, and sound in Minecraft lives in a registry — effectively a big, namespaced map from an ID to an object. Registering something wrong is the single most common reason a beginner's item "exists in code" but never shows up in the game.

Identifiers: a namespace and a path

Every registered object gets an Identifier: your mod's namespace, a colon, and a path — loom_anvil:cheapen_charm. Both halves are restricted to lowercase letters, digits, underscores, dots, and hyphens; no spaces, no capitals. This isn't arbitrary strictness — Minecraft uses these strings directly as save-file keys and resource-file paths, and capital letters or spaces would break on some filesystems.

Try it — spot the bug

Which of these would Identifier.of(namespace, path) reject or mishandle, and why: (a) Identifier.of("loom_anvil", "cheapen_charm"), (b) Identifier.of("LoomAnvil", "cheapen_charm"), (c) Identifier.of("loom_anvil", "cheapen charm")?

Reveal answer

(a) is fine. (b) has an uppercase namespace — invalid. (c) has a space in the path — also invalid. Both (b) and (c) violate the lowercase-and-limited-characters rule every registry identifier must follow.

Registering one item

You register once, early, from your ModInitializer, storing the result in a field you can reference later. Exact constructor shapes shift a little release to release — cross-check the current shape against fabric-example-mod for 1.21.11 rather than trusting any single snippet forever — but the idea is stable:

public static final Item EXAMPLE_GEAR = Registry.register(
    Registries.ITEM,
    Identifier.of(MOD_ID, "example_gear"),
    new Item(new Item.Settings())
);
Try it

Write the registration line for a single item called example_gear in your mod's namespace, exactly as above but as if you were typing it from scratch.

Reveal solution 
public static final Item EXAMPLE_GEAR = Registry.register(
    Registries.ITEM,
    Identifier.of("loom_anvil", "example_gear"),
    new Item(new Item.Settings())
);

Showing up in the creative inventory

Registering an item makes it exist; it doesn't put it anywhere a player can find it in survival or creative mode. That's a separate step — adding it to an item group (a creative-tab):

ItemGroupEvents.modifyEntriesEvent(ItemGroups.INGREDIENTS)
    .register(entries -> entries.add(EXAMPLE_GEAR));
Try it

Add your EXAMPLE_GEAR item to the ItemGroups.INGREDIENTS tab, inside onInitialize().

Reveal solution 
@Override
public void onInitialize() {
    ItemGroupEvents.modifyEntriesEvent(ItemGroups.INGREDIENTS)
        .register(entries -> entries.add(EXAMPLE_GEAR));
}
Good practice Keep every registration for one category (all items, all blocks) in its own class — ModItems, ModBlocks — with a single static register() method you call once from onInitialize(). It's the difference between finding every item your mod adds in one file, and hunting through a dozen unrelated classes six months from now.
Combine it
Move your registration into a ModItems class that registers two items (your example_gear plus one more of your choice), adds both to ItemGroups.INGREDIENTS, and exposes a single ModItems.register() method your ModInitializer calls exactly once. Explain in one sentence why calling register() twice would be a bug.
Reveal solution 
public class ModItems {
    public static final Item EXAMPLE_GEAR =
        Registry.register(Registries.ITEM, Identifier.of(LoomAnvilMod.MOD_ID, "example_gear"),
            new Item(new Item.Settings()));
    public static final Item ANVIL_SHARD =
        Registry.register(Registries.ITEM, Identifier.of(LoomAnvilMod.MOD_ID, "anvil_shard"),
            new Item(new Item.Settings()));

    public static void register() {
        ItemGroupEvents.modifyEntriesEvent(ItemGroups.INGREDIENTS)
            .register(entries -> {
                entries.add(EXAMPLE_GEAR);
                entries.add(ANVIL_SHARD);
            });
        LoomAnvilMod.LOGGER.info("Registered items for " + LoomAnvilMod.MOD_ID);
    }
}
// onInitialize(): ModItems.register();

Calling it twice would attempt to register the same Identifier twice — registries reject duplicate IDs, so the second call throws at startup instead of silently doing nothing.

Module 5

Events: the right way to hook into the game, before mixins

Fabric API ships hundreds of callback events — hooks the game engine fires for you, like ServerTickEvents.END_SERVER_TICK or UseItemCallback. This is the whole reason mixins should be your last resort, not your first: if a Fabric API event already exists for the moment you need, using it is more readable, far more resistant to breaking on a Minecraft update, and easier for another modder (or you, in six months) to understand at a glance.

An event is just a functional interface you hand a lambda to

Nothing new is happening here beyond module 2 — UseItemCallback.EVENT.register(...) takes an object matching a one-method interface, and a lambda is the natural way to provide one.

Try it

UseItemCallback has one method: interact(PlayerEntity player, World world, Hand hand). Without looking anything up, write just the lambda signature (the part before ->) you'd pass to .register(...) for it.

Reveal solution 
(player, world, hand) -> { ... }

Lambda parameters don't repeat their types — Java infers them from the interface method's signature.

The full example

public class LoomAnvilMod implements ModInitializer {
    @Override
    public void onInitialize() {
        UseItemCallback.EVENT.register((player, world, hand) -> {
            ItemStack stack = player.getStackInHand(hand);
            if (stack.isOf(ModItems.EXAMPLE_GEAR)) {
                if (!world.isClient) {
                    player.sendMessage(Text.literal("The gear hums."), true);
                }
                return TypedActionResult.success(stack);
            }
            return TypedActionResult.pass(stack);
        });
    }
}

TypedActionResult.success(stack) tells Minecraft "I handled this, stop looking for other things to do with this item use"; .pass(stack) means "not for me, carry on as normal." Returning the wrong one is a common way to accidentally block unrelated interactions.

world.isClient, and the double-run trap

A callback like this fires on both logical sides — the client predicting what's about to happen, and the server actually deciding it. Code that isn't side-checked runs on both, twice, with each side thinking it's the only one running it.

Try it — predict the bug

Here's the same callback with the if (!world.isClient) check removed, so player.sendMessage(...) runs unconditionally. What will a player actually see on screen when they use the item, and why?

Reveal answer

The message appears twice — once written by the client's own copy of this callback (running as part of its prediction), and once more when the server's authoritative copy runs and syncs a message back down. Side-checking isn't optional ceremony; it's the only thing preventing genuinely duplicated behavior.

Good practice Always check !world.isClient before doing anything server-authoritative (spawning items, changing stats, sending broadcast messages) inside an event that fires on both sides.

ServerTickEvents: a heartbeat, not a timer

Minecraft's server runs at a fixed 20 ticks per second. ServerTickEvents.END_SERVER_TICK fires once per tick, on the main server thread — it's the correct way to do "every N seconds" logic, because counting ticks stays on the thread that's allowed to touch the world; Thread.sleep or a background thread does not.

Try it

Write code using ServerTickEvents.END_SERVER_TICK that increments a counter every tick and logs once, the first time the counter passes 100.

Reveal solution 
private int tickCounter = 0;

ServerTickEvents.END_SERVER_TICK.register(server -> {
    tickCounter++;
    if (tickCounter == 100) {
        LOGGER.info("100 ticks have passed.");
    }
});
Combine it
Using UseItemCallback, detect when a player right-clicks holding your EXAMPLE_GEAR item from module 4, and — only when !world.isClient — log a message. Separately, using ServerTickEvents.END_SERVER_TICK, log "Still forging..." every 200 ticks (10 seconds). Run ./gradlew build and confirm there are no compile errors.
Reveal solution 
public class LoomAnvilMod implements ModInitializer {
    private int tickCounter = 0;

    @Override
    public void onInitialize() {
        UseItemCallback.EVENT.register((player, world, hand) -> {
            ItemStack stack = player.getStackInHand(hand);
            if (stack.isOf(ModItems.EXAMPLE_GEAR)) {
                if (!world.isClient) {
                    LOGGER.info(player.getName().getString() + " used the example gear.");
                }
                return TypedActionResult.success(stack);
            }
            return TypedActionResult.pass(stack);
        });

        ServerTickEvents.END_SERVER_TICK.register(server -> {
            tickCounter++;
            if (tickCounter % 200 == 0) {
                LOGGER.info("Still forging...");
            }
        });
    }
}

The trap this exercise checks for: reaching for Thread.sleep or a background thread instead of just counting ticks — that would touch the world off the main server thread, a reliable way to corrupt state or crash the server.

Module 6

Mixins, done right

A mixin literally rewrites Minecraft's own compiled bytecode at load time to splice your code into a vanilla method — there's no Fabric API event for it because you're changing behavior Mojang never exposed a hook for. That power is exactly why mixins deserve more care than anything else in this course: a careless one can silently break on the next Minecraft patch, conflict with another mod touching the same method, or introduce a bug nobody can reproduce because it depends on exact bytecode shape.

The rule that saves you the most pain

Reach for a mixin only after confirming Fabric API has no event for what you need. Check docs.fabricmc.net/develop/events first, every time.

Try it — decide, don't code

Three scenarios: (a) run code whenever any entity dies, (b) run code the instant a player takes damage, (c) run code at the exact moment vanilla computes how much fall damage to apply, before it's finalized. Which of these is most likely to already have a Fabric API event, and which is the kind of thing that usually needs a mixin?

Reveal reasoning

(a) and (b) are common enough that Fabric API generally covers them with a dedicated event — always check the docs to confirm for your version. (c) is different in kind: it's not "notify me when X happens," it's "let me change one specific calculation in the middle of vanilla's own method" — that's the shape of problem a generic callback usually can't expose, and where a small, targeted mixin becomes the right tool.

Anatomy of a minimal, justified mixin

When you do need one, keep it as small and targeted as possible — one injection point, one clear reason, commented with exactly what vanilla behavior you're changing and why.

@Mixin(PlayerEntity.class)
public class PlayerEntityMixin {

    // Fires right before vanilla's own attack() logic runs.
    // We only READ state here; nothing else touches attack(), so this is safe to keep small.
    @Inject(method = "attack", at = @At("HEAD"))
    private void loomAnvil$onAttackStart(Entity target, CallbackInfo ci) {
        if ((Object) this instanceof PlayerEntity player) {
            // e.g. check for the Cheapen charm and note intent to modify damage later
        }
    }
}
Try it — read the mixin

Looking at the snippet above: does loomAnvil$onAttackStart run before or after vanilla's own attack() code? Could it currently stop vanilla's code from running at all?

Reveal answer

It runs before — @At("HEAD") means the very start of the method. It cannot stop vanilla's code by itself: an injection is non-cancelling by default. To actually prevent attack() from continuing, you'd need @Inject(..., cancellable = true) and to call ci.cancel() inside the method — a separate, deliberate opt-in, not something that happens by accident.

Cancelling vanilla behavior, on purpose

@Inject(method = "attack", at = @At("HEAD"), cancellable = true)
private void loomAnvil$onAttackStart(Entity target, CallbackInfo ci) {
    if (!LoomAnvilConfig.get().enableCheapenAbility) {
        ci.cancel(); // vanilla's attack() never runs at all
    }
}

Modify the snippet above so it only cancels when a (hypothetical) boolean field onCooldown is true, instead of the config flag.

Reveal solution

Naming your injector methods defensively

Prefixing an injector method's name with your mod id (loomAnvil$onAttackStart) isn't required by Fabric, but it's cheap insurance: it keeps the name unique and self-identifying in crash logs and stack traces, and avoids the rare but nasty case where an unprefixed name accidentally matches a real method already on the target class.

Try it

A crash log shows an exception thrown inside a method called onAttackStart, with a dozen mods installed. Why is that harder to debug than one called loomAnvil$onAttackStart?

Reveal answer

The unprefixed name gives no hint which mod owns it — with a dozen mods installed, several could plausibly have written a method with that generic a name, and you'd have to cross-reference the full stack trace or bisect mods to find the culprit. The prefixed version tells you immediately.

Module 7

Config files, done right

This module doesn't assume you've built a config system before — it builds one from nothing, one piece at a time, and ends at exactly the pattern an experienced modder reaches for. By the end you'll have one class that owns the config, with loading and saving centralized, and nothing else in your mod ever touching the JSON file directly.

Why bother — what problem does a config actually solve?

Any number you hardcode (a cooldown, a discount amount, whether a feature is even on) can only change by editing code and rebuilding. A config file moves that number to something a server owner or player can edit in a text editor, with no recompiling.

Try it — think it through

Name one number or on/off switch in a mod that a server owner would plausibly want to change without recompiling.

Example answers

Whether a feature is enabled at all; a cooldown or duration; a spawn rate or drop chance; a price or discount amount. Anything a server owner might reasonably want to tune per-server without touching Java.

What Gson actually does: JSON, mapped field by field

JSON is just nested text — braces, keys, and values. Gson is a library that reads a JSON file and fills in a Java object's fields by matching key names to field names, automatically, with no code from you describing the mapping.

Try it — read, don't write

Given this JSON: {"enabled": true, "cooldown": 150} and this class: boolean enabled; int cooldown; — after Gson.fromJson(...) parses it into an instance, what are the two field values?

Reveal answer

enabled = true, cooldown = 150 — Gson matches each JSON key to the Java field with the identical name and converts the value to that field's type. No manual parsing code required.

Step 1: the fields, with real default values

Every field gets a default value right on its declaration — this matters more than it looks, and you'll see exactly why in a few steps.

public class LoomAnvilConfig {
    public boolean enableCheapenAbility = true;
    public int cheapenCooldownTicks = 200;
}
Try it

Write a class WelcomeConfig with two fields: a String welcomeMessage defaulting to "Welcome!", and an int maxPlayers defaulting to 20.

Reveal solution 
public class WelcomeConfig {
    public String welcomeMessage = "Welcome!";
    public int maxPlayers = 20;
}

Step 2: where the file actually lives

FabricLoader.getInstance().getConfigDir() returns the path to Minecraft's shared config/ folder — every mod's config lives there, side by side, which is why you resolve your own filename inside it rather than picking an arbitrary path.

    .getConfigDir().resolve("loom_anvil.json");
Try it

Step 3: loading, walked through line by line

This is the part that actually needs the try/catch from module 2 — reading a file can fail (missing, corrupted, unreadable), and none of those should crash your mod's startup.

private static LoomAnvilConfig load() {
    try {
        if (Files.exists(PATH)) {
            try (Reader reader = Files.newBufferedReader(PATH)) {
                LoomAnvilConfig cfg = GSON.fromJson(reader, LoomAnvilConfig.class);
                if (cfg != null) return cfg;
            }
        }
    } catch (IOException e) {
        LoomAnvilMod.LOGGER.warn("Couldn't read config, using defaults", e);
    }
    LoomAnvilConfig fresh = new LoomAnvilConfig();
    fresh.save();
    return fresh;
}
Checkpoint

Walk through load() line by line for the very first time your mod ever runs, before any config file has been created. What actually happens?

Reveal answer

Files.exists(PATH) is false, so the whole inner block is skipped — no exception, nothing to catch. Execution falls through to new LoomAnvilConfig(), which uses the field defaults from step 1, then immediately calls save() to write that default config out as a real file, and returns it. The very next launch, the file exists and gets read back instead.

Step 4: saving

public void save() {
    try (Writer writer = Files.newBufferedWriter(PATH)) {
        GSON.toJson(this, writer);
    } catch (IOException e) {
        LoomAnvilMod.LOGGER.warn("Couldn't save config", e);
    }
}
Try it

In one sentence: why does save() also need a try/catch, given that you're the one calling it and presumably wrote correct code?

Reveal answer

Writing to disk can fail for reasons that have nothing to do with your code being correct — a read-only filesystem, a full disk, permissions — and none of those should crash the mod either.

Step 5: one entry point, get()

Nobody outside this class should call load() directly — a single static get() loads once, caches the result, and hands it out from then on.

private static LoomAnvilConfig instance;

public static LoomAnvilConfig get() {
    if (instance == null) instance = load();
    return instance;
}

// anywhere else in the mod:
if (LoomAnvilConfig.get().enableCheapenAbility) { ... }
Try it

In one sentence, why should every part of the mod call LoomAnvilConfig.get() instead of each writing its own file-reading code?

Reveal answer

So the file's location, its parsing, and its fallback-to-defaults behavior exist in exactly one place — if any of that ever needs to change, there's one method to fix instead of hunting down every place that reads the file.

Why this shape Three things make this "done right" instead of "works for now": (1) a single get() entry point means nobody else needs to know the file even exists, (2) missing or corrupt config never crashes startup — it falls back to sane defaults and rewrites the file, and (3) fields are plain public values with sensible names, so the JSON a player edits by hand looks exactly like the fields in your code.
Combine it

Two parts:

1. Add a third field, maxCharmsPerPlayer (default 3), to LoomAnvilConfig. Explain what happens the first time an existing player, who has an old saved config file from before this field existed, loads your mod.

Gson fills in fields missing from the saved JSON using the class's own default field initializers — so an old config file simply gets maxCharmsPerPlayer = 3 in memory, and the next save() writes the now-complete file back out. Module 8

Testing without a screen

This is the module that actually makes iPad-only development work long-term. Fabric bundles Minecraft's own GameTest framework — automated tests that spin up a tiny slice of a real world, run assertions against it, and report pass/fail, with no window, no rendering, and no human clicking around. Server-side game tests run automatically as part of ./gradlew build — the same command from module 1.

Anatomy of a GameTest method

A @GameTest method receives a GameTestHelper — call helper.fail(message) if something's wrong, and you must always call helper.succeed() at the end.

public class LoomAnvilGameTest implements FabricGameTest {

    @GameTest(templateName = EMPTY_STRUCTURE)
    public void exampleGearIsRegistered(GameTestHelper helper) {
        boolean registered = Registries.ITEM.containsId(
            Identifier.of(LoomAnvilMod.MOD_ID, "example_gear"));
        if (!registered) {
            helper.fail("example_gear was never registered");
        }
        helper.succeed();
    }
}
Try it — spot the bug

Someone writes a test whose assertion logic is completely correct, but they forget to call helper.succeed() anywhere in the method. What happens when the thing being checked is actually fine?

Reveal answer

Without an explicit succeed(), the test framework never receives confirmation that the test finished and passed — it's left looking like it's still running until it eventually times out, which reads as a failure even though the logic you cared about was correct the whole time. Every GameTest must explicitly call succeed(); there's no "no news is good news."

Registering the test class

Register it as its own entrypoint in fabric.mod.json, separate from your normal mod entrypoints:

"entrypoints": {
  "main": ["com.example.loomanvil.LoomAnvilMod"],
  "fabric-gametest": ["com.example.loomanvil.LoomAnvilGameTest"]
}
Try it

Reveal solution 
"entrypoints": {
  "fabric-gametest": ["com.example.loomanvil.CheapenGameTest"]
}

Run ./gradlew build: if the test fails, the build fails with your message in the log, right there in the Codespaces terminal — that failure message is your entire feedback loop now, instead of a screen.

Good practice Write a GameTest the moment you finish anything you'd otherwise want to "just check in game" — a registration, a config default, a mixin's side effect on a value you can read back. It costs a few lines now and saves you from ever needing a graphical client just to sanity-check that a feature still exists after a refactor.

Module 9

Networking: talking between client and server

The client and server are two separate programs (even in singleplayer, which quietly runs a server in the background) exchanging messages over a connection. Anything not covered by an existing Fabric API event — a custom button press, a custom screen submitting data — needs a custom payload to cross that gap.

A payload is a record (module 2, paying off)

Modern Fabric networking represents a packet as a Java record implementing CustomPacketPayload — the immutable-bundle-of-data feature from module 2 turns out to be exactly what a network message is.

public record CheapenRequestPayload(int charmSlot) implements CustomPacketPayload {
    public static final CustomPacketPayload.Id<CheapenRequestPayload> ID =
        new CustomPacketPayload.Id<>(Identifier.of(LoomAnvilMod.MOD_ID, "cheapen_request"));

    public static final PacketCodec<RegistryByteBuf, CheapenRequestPayload> CODEC =
        PacketCodec.tuple(PacketCodecs.INTEGER, CheapenRequestPayload::charmSlot, CheapenRequestPayload::new);

    @Override
    public CustomPacketPayload.Id<? extends CustomPacketPayload> getId() {
        return ID;
    }
}

The CODEC is what turns your record's fields into bytes and back — exact codec-building helpers shift between versions, so cross-check the current shape against docs.fabricmc.net/develop/networking for 1.21.11.

Try it

Without worrying about the codec syntax, write just the record header for a payload called PingPayload carrying one String message field, implementing CustomPacketPayload.

Reveal solution 
public record PingPayload(String message) implements CustomPacketPayload { }

Registering, then sending

Register the payload type once, from your common (non-client, non-server-only) initializer, then send it from whichever side originates the message:

// registration, in onInitialize():
PayloadTypeRegistry.playC2S().register(CheapenRequestPayload.ID, CheapenRequestPayload.CODEC);

// sending, client -> server:
ClientPlayNetworking.send(new CheapenRequestPayload(2));

// receiving, on the server:
ServerPlayNetworking.registerGlobalReceiver(CheapenRequestPayload.ID, (payload, context) -> {
    // runs on the server; context.player() is who sent it
});
Try it — name the direction

playC2S() registers a client-to-server payload. What would you call the registry method for a server-to-client payload, and which networking class (ClientPlayNetworking or ServerPlayNetworking) would send it?

Reveal answer

PayloadTypeRegistry.playS2C(), and it would be sent from ServerPlayNetworking.send(player, payload) — the server pushing a message down to a specific client.

The single most important rule in this module Never trust data a client sends you. A client is code running on someone else's machine — a modified or hacked client can send a server any payload with any field values it wants, whether or not the real game UI would ever produce them. Every field on an incoming server-bound payload needs the same validation you'd give user input anywhere else: is this slot index actually in range? Does this player actually have this item? Never assume the client-side checks that normally prevent an invalid request ran at all.
Try it

Reveal solution 
if (payload.charmSlot() < 0 || payload.charmSlot() >= inventorySize) {
    return; // ignore an out-of-range request instead of crashing or corrupting state
}

Module 10

Data generation: writing JSON with Java instead of by hand

Recipes, loot tables, and tags are all plain JSON files Minecraft reads at load time. Hand-writing them works, but gets error-prone and repetitive past a handful of items. Fabric's data generation API lets you describe the same content in Java, then run a Gradle task that writes the correct JSON files for you.

Why generate instead of hand-write

A hand-written recipe JSON file with a typo'd item id fails silently at load — the recipe just doesn't exist, with no compile-time warning. A datagen provider references your actual registered Item objects from module 4, so a typo becomes a compile error instead of a silent runtime gap.

Try it — think it through

In one sentence: why is referencing ModItems.EXAMPLE_GEAR directly in a datagen provider safer than typing the string "loom_anvil:example_gear" into a hand-written JSON file?

Reveal answer

The Java reference is checked by the compiler — rename or remove the item and every provider referencing it fails to compile, forcing you to fix it. A typo'd string in JSON compiles fine and just silently fails to match anything at runtime.

Registering a data generator entrypoint

Datagen runs as a separate Gradle task (runDatagen), driven by a DataGeneratorEntrypoint registered in fabric.mod.json, kept entirely separate from your normal mod code so it never ships inside the actual mod jar:

public class LoomAnvilDataGenerator implements DataGeneratorEntrypoint {
    @Override
    public void onInitializeDataGenerator(FabricDataGenerator.Pack pack) {
        pack.addProvider(LoomAnvilRecipeProvider::new);
    }
}
"entrypoints": {
  "fabric-datagen": ["com.example.loomanvil.LoomAnvilDataGenerator"]
}
Try it

Which fabric.mod.json entrypoint key registers a data generator — "main", "client", or "fabric-datagen"?

Reveal answer

"fabric-datagen" — its own dedicated key, run only by the runDatagen Gradle task, never during normal play.

A recipe provider, conceptually

A recipe provider's generate() method builds recipe definitions in Java (shaped crafting, smelting, whatever you need) and hands them to a JSON exporter — exact builder method names shift by version, so check docs.fabricmc.net/develop/data-generation for 1.21.11's exact shape rather than a hardcoded snippet here.

Checkpoint

Reveal answer

Most likely, the fabric-datagen entrypoint was never wired up in fabric.mod.json — the same class of mistake as module 3's mismatched entrypoint, just for a different entrypoint key. Fabric Loader only runs what's actually declared.

Screens & HUD: client-only rendering

Everything in this module lives strictly on the client side — it's the payoff of module 3's client/server discipline. A custom inventory-style screen, or drawing something on the player's HUD, is pure presentation with no world-authoritative logic, which is exactly why it's dangerous to let it touch anything server-side directly.

A Screen is a client-only class, registered client-only

A custom Screen subclass belongs under your ClientModInitializer's package, same as module 3's rule — referencing it from a class that also runs on a dedicated server crashes that server the moment the class loads, even if the screen is never actually opened there.

public class CheapenScreen extends HandledScreen<CheapenScreenHandler> {

    }
}
Try it — apply an earlier rule

In one sentence, using module 3's reasoning: what would happen if CheapenScreen were accidentally referenced from your main ModInitializer class instead of staying isolated in client-only code?

Reveal answer

A dedicated server loads and runs every class your ModInitializer touches — the moment it tries to load a class that references rendering-only types that don't exist on a server, it crashes with a ClassNotFoundException, exactly as module 3 described for any client-only class.

HUD rendering: a callback, like module 5

Drawing something every frame (a cooldown indicator, a custom counter) uses a Fabric API rendering callback — same shape as the events from module 5, just firing on render instead of on tick or interaction:

HudRenderCallback.EVENT.register((context, tickDelta) -> {

        context.drawText(client.textRenderer, "Cheapen ready", 10, 10, 0xFFFFFF, true);
    }
});
Try it

This callback reads a config value every single frame (potentially 60+ times a second). Given what module 7 taught about LoomAnvilConfig.get() being cheap to call repeatedly (it just returns a cached instance after the first load), is that a performance concern here? Explain briefly.

Reveal answer

No — get() returns the already-loaded, cached instance; it doesn't re-read the file from disk each call. Reading a boolean field off an object already in memory, even 60 times a second, is negligible. The expensive part (disk I/O) only happens once, at first load.

Good practice A screen or HUD element should only ever display state, never decide it — if a player could change game outcomes by having a modified client draw or submit something different, that decision belongs on the server, validated the way module 9 described, not trusted from the client's rendering code.
